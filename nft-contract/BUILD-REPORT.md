## Decision: pre-assigned tiers (v2 — supersedes the v1 mint-time draw)

**Problem found after v1 (72/72 green):** v1 drew each paid mint's tier from block data at mint time. But the collection's metadata is statically hosted (GitHub Pages): a static `<tokenId>.json` is written before launch and cannot know which tier the contract will draw for that ID at mint time. Metadata and `tierOf()` could therefore disagree — which breaks marketplaces and the game's own card checks. A draw-based tier is fundamentally incompatible with static metadata.

**Fix (as now built):** tiers are a pure function of token ID, assigned before launch in two blocks that mirror the two mint lanes (the owner's known two-lane ID-space pattern, cf. the AgentDraw Pass lanes):
- **Free block, IDs 1–500 — all ROOKIE.** `mintFree()` mints the next ID in this block via a sequential pointer (`nextFreeId`); all v1 free-lane rules unchanged (Agent ID gate, 1 free/wallet, 0 BNB, counts toward the 5/wallet total cap).
- **Paid block, IDs 501–2,222 (1,722 cards) — tiers pre-assigned** by an off-chain fair shuffle: ROOKIE **833**, PRO **556**, NITRO **244**, CHAMPION **89**. `mintPaid()` mints the next ID in this block via a sequential pointer (`nextPaidId`) at exactly 0.001 BNB, and the token's tier is its pre-assigned tier. Collection totals stay exactly at the caps: ROOKIE 1,333 (= 500 + 833) / 556 / 244 / 89 = 2,222.
- The assignment is generated by `tools/generate-assignment.js` — a deterministic shuffle seeded from the fixed string `"crown-racer-cards-launch-shuffle-v1"` (counter-mode SHA-256 stream + Fisher–Yates; re-running reproduces `nft/assignment.json` byte-for-byte) — and passed to the contract as a packed `bytes` constructor argument (2 bits per token, 1,722 tokens = **431 bytes**), immutable after deployment. The constructor rejects any other length. `tierOf(tokenId)`: IDs 1–500 → ROOKIE; IDs ≥ 501 → unpack from the assignment. The block-data draw and the fall-through logic are **removed**.
- Fairness, stated honestly in the contract and here: tiers are **NOT drawn at mint time**. They were fixed by a pre-launch shuffle whose seed and the **SHA-256 commitment of `assignment.json`** — `70bd79e7ef21b9251d5bc6b67ccbd3d4f4a706a5b96477378636a825fbf81510` (equals `sha256sum nft/assignment.json`) — are published in the repo **before the mint opens**. Anyone can regenerate the assignment from the seed, check it against the commitment, and compare it with the on-chain `paidAssignment` bytes: provably fair, committed before launch, revealed per token as the paid block mints out.
- Consequence for metadata: since the tier is fixed per ID before launch, metadata generation simply reads tiers from `nft/assignment.json` (free block = ROOKIE) and `<tokenId>.json` can never disagree with `tierOf()`.

## Locked spec (as built)

**Tiers & hard caps** (sum = supply): ROOKIE (0) **1,333** · PRO (1) **556** · NITRO (2) **244** · CHAMPION (3) **89** — reached exactly at sell-out by construction (500 free ROOKIE + the paid assignment's 833/556/244/89).

**Free lane — `mintFree()`**
- Value 0 (the function is not payable), caller must hold a Binance .ai Agent ID (`balanceOf > 0` on the registry), free block = IDs **1–500** (sequential pointer), max **1** free mint per wallet, always mints a **ROOKIE**. The free block is part of the 2,222, not additional.

**Paid lane — `mintPaid()`**
- Exactly **0.001 BNB**. Mints the next paid-block ID (**501–2,222**, sequential pointer) with its pre-assigned tier from the constructor's packed assignment bytes. No draw, no fall-through, no mint-time randomness of any kind. When the paid pointer passes 2,222 the lane reverts "Sold out"; the free lane reverts once its block is exhausted.

**Cross-lane rules**
- Max **5 minted cards per wallet in total across BOTH lanes** (`mintCountOf`); a free mint counts toward the 5, and a wallet at 5 paid mints cannot free-mint.
- Lanes run **in parallel** — the paid lane is never gated on the free lane (owner's standing design rule). The test suite proves a paid mint lands before any free mint, and that paid minting still works after the free quota is exhausted.
- `mintOpen` starts **false**; owner toggles via `setMintOpen(bool)`.

**Owner & funds**
- `withdraw()` — owner only, sends the contract's **full BNB balance** (paid-mint proceeds).
- `setBaseURI(string)` — owner only, and **restricted to while the mint is closed**, so metadata cannot be swapped under buyers mid-mint.
- `transferOwnership(address)` — owner only, zero address rejected.

**Metadata**
- Constructor: `CrownRacerCards(address agentId_, string baseURI_, bytes assignment_)`. Production registry `0x60B9262456dE011F7d15a54CdD8c48bAaa8B022F`; production baseURI `https://crownrace.site/nft/metadata/`; production assignment = `nft/assignment-bytes.txt` (431 bytes, embedded in the deploy page).
- `tokenURI(id)` = `baseURI + "<id>.json"` (empty string if baseURI is empty). The hosted JSONs carry the image URL `https://crownrace.site/nft/images/<id>.png` — the contract only stores baseURI. Metadata tiers are read from `nft/assignment.json` (IDs 1–500 = ROOKIE), so hosted metadata and `tierOf()` agree by construction.

## Decisions made where the spec left room

1. **`mintFree()` is not payable.** Sending value to it reverts at the EVM level, which is the strictest form of "0 BNB". (CrownRaceGame's rookie entry instead checks `msg.value == 0` on a payable function; both work, non-payable is simpler here.)
2. ~~Fall-through order ROOKIE → PRO → NITRO → CHAMPION after a mint-time draw~~ — **v1 decision, superseded by the pre-assigned-tiers fix above**: there is no draw and no fall-through anymore; each paid ID's tier is its shuffled assignment, so the collection sells out exactly at the caps by construction.
3. **`setBaseURI` uses the restricted variant** (owner-only **and** mint closed), per the spec's preference.
4. **`withdraw()` reverts on an empty balance** ("Nothing to withdraw"), matching the CrownRaceGame house pattern.
5. **The paid lane does not require an Agent ID** — the spec attaches the Agent ID gate to the free lane only (house pattern).
6. **`CardMinted` event on every mint** (with a `paid` flag) so the site and indexers can build per-tier galleries without log archaeology.
7. **The constructor validates the assignment length only (exactly 431 bytes), not its tier counts.** Counts are guaranteed by the generator (which self-checks 833/556/244/89 before writing) and are publicly verifiable against the published commitment and the on-chain `paidAssignment`; the `tierMinted` counters expose any inconsistency at mint time. (The test suite proves a different same-length assignment deploys and drives tiers, so the length check is the only deployment gate.)
